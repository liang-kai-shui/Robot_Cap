# Robot_Cap 软件方案实测：DeepSeek Flash

日期：2026-10-05（北京时间）

代码基线：`v1-runtime-hardening` / `be0c4a3`

模型：`deepseek-flash`（官方当前指向 DeepSeek-V4.1-Flash）

## 结论

1. 原始 18 类能力任务在 54 次重复中全部成功；这说明当前 Registry、受限 Policy、Runtime 和基础动作链路能稳定承载该模型生成的简单任务。
2. 12 个复杂已知地图任务重复 3 次，最终目标成功 32/36，额外 trace 判据成功 25/36。主要落差是 `waypoint_order`；此外有 4 次 30 秒 API 读取超时。
3. 在同一组 H1–H4 世界中，完整地图一次生成成功 12/12；隐藏地图局部观测多轮执行仅成功 3/12。完整地图方案拥有明显的信息优势，不能把差距全归因于规划算法。但当前交互实现没有达到复杂隐藏地图可用的可靠性。
4. 关闭 DeepSeek 思考模式后，交互式任务的中位总耗时从 30.26 秒降到 3.61 秒，成功数仍为 3/12。超时转成 Policy 校验、动作预算和决策预算失败。速度优化单独使用不能解决规划与安全问题。

## 方法与可比性

- 四组主实验均使用仓库当前 `VirtualBackend`、相同 Runtime 默认限额和非流式 Chat Completions；每个任务重复 3 次。Provider 单次 HTTP 读取超时固定为 30 秒。除“关闭思考模式”消融外，未显式设置思考强度，故 DeepSeek 使用其默认思考模式。
- 原始任务：A1–D4 共 18 类，每类 3 次。E1、E2 是**固定 Policy** 的安全测试，各 3 次，不计入模型能力成功率。
- 复杂任务：N、F、AS、SP、MX 共 12 类，每类 3 次；完整地图与起点给模型。`task_success` 只看最终目标；`complex_success` 另看 trace 行为。
- 同题配对：H1–H4 的世界、起点、目标不变。一次生成组提供完整地图，并把指令改为“已知地图”；交互组维持“地图未知”，只给局部位姿、前向 2 米内测距及上一轮结果。两组的信息条件不同，配对用于量化当前产品形态的实际取舍。
- 消融：仅对 H1–H4 交互组添加官方 `thinking: {type: disabled}`，其余任务、Prompt、超时、Runtime 与重复次数相同。
- `total_ms` 包括模型请求、校验、Worker 执行与评估。token 合计仅包括 API 已返回 usage 的请求；读取超时请求的服务端耗费未知。以下均为真实接口调用结果，离线 reference/mock 结果不算模型成绩。

## 逐任务结果

### 原始能力任务

A1–A5、B1–B5、C1–C4、D1–D4 **每题均为 3/3**。没有校验、碰撞或 Policy 计算超时失败。平均每次已返回 usage 的请求为约 544 输入 token、284 输出 token；中位模型响应 1.41 秒。

| N1 | 3/3 | 0/3 | 三次均到终点，但 `waypoint_order` 未命中 |
| N2 | 2/3 | 0/3 | 一次 API 读取超时；其余未命中 `waypoint_order` |
| N3、N4 | 各 3/3 | 各 3/3 | 通过 |
| F1、F2 | 各 3/3 | 各 3/3 | 通过 |
| AS1 | 3/3 | 3/3 | 通过 |
| AS2 | 1/3 | 1/3 | 两次 API 读取超时 |
| SP1、SP2 | 各 3/3 | 各 3/3 | 通过 |
| MX1 | 2/3 | 0/3 | 一次 API 读取超时；其余未命中 `waypoint_order` |

按类别的严格判据成功率：navigation 6/12、feedback 6/6、active sensing 4/6、speed 6/6、mixed 3/6。36 次里 `waypoint_order` 出现 11 次，其中 7 次最终目标已经成功。当前评分器仅检查**每次 move 结束时**的位姿是否落在检查点附近；路径穿过检查点但没有恰好在此结束动作，也会被记为未命中。因此 25/36 是当前 trace 规则的成绩，不能简单解释为仅有 25 次实际穿过通道。需要保留最终目标与严格判据双指标，并重新审查检查点的语义。

| H2 近障碍 | 3/3 | 0/3 | 0/3 | 14.30 秒 | 30.25 / 4.39 秒 |
| H3 中距障碍 | 3/3 | 0/3 | 0/3 | 9.19 秒 | 54.85 / 3.55 秒 |

默认思考交互组的 9 次失败：7 次 `PolicyGenerationError`、1 次 `WorldBoundaryError`、1 次 `CollisionError`。复杂已知地图组的 4 次 `PolicyGenerationError` 可从保存的错误文本确认均为“read operation timed out”；交互结果只保存了错误类型，没有保存错误消息，故不能逐条确认其 7 次错误的底层原因。不过对应运行通常接近 30 秒读取上限。一次越界案例中，Policy 转向后复用了转向前的测距来决定移动距离；虚拟世界拦下了动作。

关闭思考后的 9 次失败：`UnsafePolicyError` 4 次、`ActionLimitExceeded` 2 次、`DecisionLimitExceeded` 2 次、`RobotActionError` 1 次。默认思考组成功返回的单轮 Policy 中位 9 行、最长 41 行，说明“短 Policy”尚未成为可执行的硬约束。关闭思考降低了响应耗时和输出 token，但复杂隐藏地图的成功率没有改善。

## 判断与下一步软件优先级

1. **先约束交互决策粒度。** 将每轮有效动作限制为一次有限 `move` 或 `turn`，执行后必定重新观测；转向前的前向距离不得用于转向后的移动。这能直接消除本次观察到的陈旧测距风险，也缩短生成代码。保持现有 Robot API，不引入新 DSL。
2. **在可信侧加入模拟安全保护。** 使用当前方向的最新测距、clearance 和允许的单步距离，在 dispatch 前拒绝会越界或碰撞的命令。Prompt 只能降低错误概率，不能承担物理安全边界。
3. **把模型请求超时改为可配置并保存底层错误。** 分别报告模型生成超时、Policy 计算超时与动作超时。用相同任务、例如 30 秒与 60 秒两档，测清“等待更久能成功多少”与延迟代价；不能把接口超时算成模型规划错误。
4. **保留思考模式作为可测配置。** 对简单局部动作，可先试关闭思考或较低 effort；只有在第 1、2 点的控制措施生效后，再比较成功率与成本。当前消融证明了加速有效，但没有证明可用性提升。
5. **扩展配对世界后再作部署判断。** 当前只有 4 种静态矩形障碍、同一终点、理想位姿和理想测距，每条件只有 3 次。后续应加入观测噪声、测距盲区、动态障碍和不同目标，同时保持已知地图与局部交互两组的起点、目标和世界严格配对。此时仍不需要硬件或 Policy Reuse。

这轮没有更改生产 Runtime、Benchmark 任务或 Policy Reuse。参考规则曾完成 H1–H4 4/4，仅用于证明场景可解；本报告的模型成绩均来自 DeepSeek API。
