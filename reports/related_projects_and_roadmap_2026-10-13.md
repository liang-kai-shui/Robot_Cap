# Robot CaP 相似项目调研与优化建议

资料检索与整理：2026-10-12 至 2026-10-13（Asia/Shanghai）；整理完成：2026-10-13。对象：本仓库的 Python CaP 高层、WebUI、ESP32-S3 固件和双 N20 编码电机小车。**本报告只提出建议，没有实现下述功能，没有安装外部框架，也没有执行实车动作。**

本地功能基线为 `041d51f`：v1.9 / PARAM2 / `pwm-stream-v2`。仓库阅读入口整理见 `998b3f4`。外部资料依据访问当日的作者论文、官方仓库或文档；分支和网页可能继续变化。本次是面向本车的选择性调研，不是穷尽所有机器人项目的文献综述。

## 1. 建议优先走哪条路线

我建议把项目定位为：**低成本双轮小车上的、可检查和可复现的自然语言控制与技能复用实验平台。**

近期先做三件事：把运动与故障语义稳定下来；用统一时间线找出真实延迟；在已有 Policy 复用上增加参数化技能、适用条件与验证证据。当前已有一条完整 CaP 执行链路，值得继续整理和验证，而不是立即换成一个更大的代理框架。

中期补齐独立位置验证、校准与无线运行条件，再考虑 ROS 2、地图导航和视觉目标。VLA、强化学习、自主探索和自动修改运行中固件都不适合作为当前下一步：本车缺少相应视觉观测、任务数据和独立成功判据。以下优先级是结合本项目的判断，不是外部论文已经证明的本车收益。

## 2. 本项目已经有什么，缺口在哪里

阅读依据：[系统架构](../docs/ARCHITECTURE.md)、[CAP 接入核对](../docs/CAP_INTEGRATION_AUDIT.md)、[当前状态](../docs/PROJECT_STATUS.md)，以及 `agent/physical_policy.py`、`agent/physical_context.py`、`policy/reuse.py`、`robot/backends/esp32_serial.py`、`webui/controller.py` 和固件主循环。

| 层次 | 已有能力 | 下一步的实际缺口 |
| --- | --- | --- |
| 语言与计划 | DeepSeek、完整计划预览/校验、分段反馈审核、明确参数动作 | 任务语义仍较依赖提示词；缺少独立的结构化意图与歧义处理层 |
| 可信执行 | Registry、AST、独立 Worker、动作预算、串口结果与停稳匹配 | IPC 动作 ID 不等于 MCU 协议级动作 ID；故障恢复状态和原因可进一步结构化 |
| 复用 | CLI/WebUI 共享已验证完整 Policy，匹配明确数字任务，失败条目失效 | 不是通用参数化技能库；未把全部硬件校准/固件构建条件作为技能有效性依据 |
| 记忆 | 同次开机的任务记录、已完成动作引用；重启清空引用 | 长会话提示会增长；需要区分完整日志、模型当前工作上下文、持久技能知识 |
| 运动 | 距离/角度闭环、测距接近；手动实际 PWM、双轮编码器反馈 | PWM 与车速不是同一物理量；手动独立最高转速未标定；制动余量和两轮差异尚需系统测量 |
| 传感与界面 | BMI、ToF、车速/轮速估计、3D 姿态、错误区与日志 | 姿态安装变换、近场测距、拖线和地面打滑都会影响解释；缺少统一回放与故障片段 |
| 评测 | 模拟基准、私有真值评分、实车 Episode/计时 | 实车无独立地面位姿；`execution_success` 不能代替 `task_success` |

必须保留的事实：前方普通停车保护为 OFF；没有后方/侧方观测；ToF 不等于二维地图；BMI 相对 yaw 不等于绝对航向；编码器距离不等于地面位置。40% PWM 遥控已有用户验证；80% 曾触发旧版目标转速检查，v2 已修复、烧录并完成静止确认，尚无修复后高 PWM 运动结论。[PWM 说明](../docs/MANUAL_PWM.md)

## 3. 检索方式与材料选择

从用户给出的 [Awesome Coding Agents for Robot Learning](https://github.com/harooos/awesome-coding-agents-for-robot-learning) 出发，并独立检索了 CaP/技能复用、ROS 机器人代理、ESP32 差速小车、micro-ROS、网页遥控与观测工具。该清单适合找研究方向；具体判断转向原始论文与作者仓库，不把清单中的概括直接当成已验证的部署能力。

重点检索方向包括 `Code as Policies / skill library / Policy Bank`、`robot embodied agent harness`、`ESP32 differential drive micro-ROS`、`Linorobot2 web cockpit`、`robot teleop visualization`。最终选取下表 **15 个项目或组件**。没有按 GitHub 星数排名；没有克隆、安装或复跑外部项目，因此“适合借鉴”不代表已经兼容本车。

## 4. 当前最值得做的改进

### 4.1 先把“能力可用”和“任务有帮助”分开

SayCan 的可执行性判断与 Thea 的具身配置说明值得借鉴，但本车应先用已有状态做确定性检查，而不是让模型自行猜硬件健康。建议未来用一份统一能力视图驱动模型提示、计划校验和网页禁用原因。[SayCan](https://say-can.github.io/) · [Thea](https://github.com/EIT-HAI/Thea)

| 动作 | 需要核对的条件 | 不应混用的判断 |
| --- | --- | --- |
| 手动 PWM | 连接、停止/租约状态、编码器和底层故障 | 不依赖 BMI 航向；PWM80%不等于转速目标80% |
| 距离前进/后退 | 当前闭环要求的编码器和有效 BMI | 前方 ToF 有效不代表后方可通行 |
| 转角 | 有效相对 yaw、允许角度、停稳 | 不需要通过前方净距推算转角；不能当作绝对朝向 |
| 测距接近 | 新鲜有效 ToF、适合的目标净距和当前固件闭环条件 | 生成时的距离只是规划参考，执行中必须继续测量 |
| 状态/观测 | 实际传感器有效性与时间 | 不应用旧有效值填补当前无效值 |

这能针对本会话曾发生的全局拒绝、旧故障影响新任务等现象，但**相关提示修复已经存在**；建议的是进一步把约束做成统一契约，而不是声称现在没有任何检查。保留故障锁定，不能用模型一句“应该安全”恢复运动。

验收建议：同一设备快照下，提示、校验与 UI 对可用动作给出一致判断；BMI 无效时分别验证手动、转角、测距动作的实际边界；一次软件拒绝不永久污染以后健康的明确任务。

### 4.2 用物理参数解释运动，不再混用 PWM 与速度

最近80%误停说明了一个具体问题：模式换成直接PWM后，保护仍沿用闭环2200 counts/s目标的两倍阈值。v2已修复这一相对阈值误用。后续应把“原始占空比调试模式”和“物理速度闭环模式”明确区分，分别记录请求值、实际输出和实测轮速。[本地修复说明](../docs/MANUAL_PWM.md)

建议先记录空载与地面行走时，左右轮各方向的 PWM—轮速关系、起转区间、供电与表面条件、停止后的滑行距离，再决定速度/加速度限制和制动策略。不要假设PWM线性对应轮速；不要从一次40%表现推断100%极限；**不做堵转电流测试**，也不把架空无负载数据当成地面制动数据。

车轮直径43mm已知；轮间距、左右有效轮径、编码计数比例和车体到IMU的完整安装关系仍应独立记录。未来再加入按 m/s 和 rad/s 的遥控模式，保留PWM作为明确的手动调试入口，不让模型直接访问电机占空比。[差速控制器参数与限制](https://control.ros.org/rolling/doc/ros2_controllers/diff_drive_controller/doc/userdoc.html)

建议验收：分别报告编码器距离与尺测地面距离误差、左右差异、转角误差、停止余量及失联停车行为；保留失败样本。独立手动最高转速限制应根据实际数据和硬件规格制定，目前没有这项标定结果。

### 4.3 给串口反馈统一身份与故障语义

当前有限动作依赖串口顺序、目标匹配和新READY，Runtime的command ID主要在IPC层；持续遥控另有session。建议未来在协议中明确 `boot_id`、动作ID、模式、序号、反馈时间及错误类别；日志与控制报文使用不同的类型，必要时分流传输。

协议级动作ID的价值是匹配本次 START/RESULT/DONE、识别重放和迟到报文；**不是允许超时后自动重发电机动作**。完整有限动作仍先校验、不排队；STOP与失联截止仍在可信侧和MCU独立执行。

建议把页面的“串口断开”“固件已停机但锁定”“传感器无效”“软件拒绝”“动作超时”分开显示。故障片段包括故障前后数秒的轮速、PWM、控制周期和传感器有效性。根据明确状态提供停止、静止归零或复位说明，而不是每种情况都提示重新连接。当前不自动实现任何恢复动作。

### 4.4 用证据回放替代反复猜故障

现有 WebUI 已有日志、轮速、3D 和错误区。下一步可做一个共享时间轴：自然语言任务、生成代码、动作开始、PWM变化、编码器、yaw/ToF、STOP与故障都可对齐；支持只读回放及导出故障窗口。参考 Foxglove 的遥控/观测分工与 Cockpit 的设备流程，不必直接替换界面。[Foxglove](https://docs.foxglove.dev/docs/visualization/panels/teleop) · [Cockpit](https://github.com/hippo5329/linorobot2-cockpit)

回放必须明显标成历史，禁用运动控制，绝不把历史运动报文重新发给设备。生成代码、拒绝原因和设备故障并列展示，避免把模型错误与控制错误混为一种。当前“相同文字重复更新导致选区闪烁”已修复，不再列为待实现功能。

## 5. 自然语言速度：先减少不必要工作，再换模型

### 5.1 已有优化不能再次当作新功能

本项目已实现稳定提示前缀、模型配置、WebUI本地段间审核、避免不必要的重复STOP，以及CLI/WebUI共享的明确任务Policy复用。这些是现有基础。服务端前缀缓存命中由提供商决定，不能和本地策略复用混称一种缓存。[CAP核对](../docs/CAP_INTEGRATION_AUDIT.md)

RHO的启发是把常用行为的验证和优化移到执行前；CaP-X也公开了从成功试验整理可复用函数的工具。建议借鉴这个工作位置，而不是复刻其昂贵的优化流程或把其仿真成绩写成本车成绩。[RHO](https://rho-robotics.github.io/) · [CaP-X技能编译说明](https://github.com/capgym/cap-x/blob/main/scripts/skill_library_compilation/README.md)

### 5.2 将耗时拆成可比较的指标

| 环节 | 当前可观察 / 建议补充 | 优化原则 |
| --- | --- | --- |
| 意图处理与复用检索 | `policy_lookup`、命中来源；未来加意图解析耗时 | 明确常用任务走已验证模板；歧义不能为了快而猜 |
| 模型请求 | 总耗时、TTFT、Token、模型/设置、提供商缓存用量（若有） | 同一任务集对照；不能只凭一次响应评价模型 |
| 校验与准备 | AST、能力、预算、动作前健康停稳 | 不删除必要检查；只去掉已证明重复的工作 |
| 动作执行 | 发指令→START、固件drive、STOP→RESULT→DONE→READY | 计划时间与实际运动时间分开，识别停稳等待是否主导 |
| 段间审核 | 本地/模型、次数、停稳时间 | 明确机械反馈优先用本地；语义状态变化才触发高层判断 |
| 整项任务 | 全链路p50/p95、成功/拒绝/故障、成本 | 更快但误动更多不算优化成功 |

建议实验固定任务、动作预算、硬件条件、模型与采样设置，分别测首次生成、重复命中、上下文引用、动态测距和失败任务。可把每组至少20次作为首轮采样计划；这是建议规模，不是已有20次实车数据，也不足以证明低概率故障已消失。

### 5.3 不让网络延迟进入电机闭环

保留电脑高层与ESP32本地控制的分工。遥控当前有65ms浏览器心跳、服务端200ms截止和MCU250ms租约；网页显示的往返时间不是电机响应时间。需要测“网页输入→服务收到→MCU接受→编码器开始变化”的多个时间戳，并说明时钟同步/偏差，不能直接相减不同时钟的绝对时间。[现有遥控说明](../docs/ROVER_V19.md)

先测UART控制与日志占用、主循环周期、后端排队、SSE刷新与网页帧率。若日志阻塞控制，考虑限频/异步日志或控制与调试通道分离。动画插值不会改善实测控制延迟；改UDP也不会自动解决本地阻塞，还会引入丢包、乱序、认证和重放处理。现在无需仅为了“低延迟”立即迁移ROS或网络协议。

不建议让机器人在流式输出半段未经校验的模型代码时开始执行；这是把尚未完成的计划变成实体动作。未来可以预生成候选或提前加载技能，但必须在执行前完成本次校验和授权。

## 6. 从完整 Policy 复用走向技能库

LMPVC的可教授Policy Bank、Voyager的代码技能检索，以及CaP-X的成功试验技能编译，各自提供了不同参考。它们不等价于当前的“完整明确数字任务代码复用”，也不代表随意相似匹配就能可靠运行实体机器人。[LMPVC](https://arxiv.org/abs/2506.22028) · [Voyager](https://voyager.minedojo.org/) · [CaP-X](https://github.com/capgym/cap-x/blob/main/scripts/skill_library_compilation/README.md)

建议分三步：

1. **规范已有条目。** 保留完整任务、代码、API契约和验证来源；增加硬件/固件构建、校准版本及数据条件说明。先解决条目能否在当前车上使用，而不是先增加向量数据库。
2. **批准少量参数化技能。** 例如有界直行、相对转向、保持目标前方净距。每种技能有固定实施方式、参数范围、传感器前置条件、成功/失败后置条件、动作预算与停止行为；参数来自用户意图并通过可信校验。
3. **组合成任务配方。** 配方可以引用多个已验证技能，但整项预算与停止规则仍统一校验。语义检索只负责推荐候选；候选必须通过契约和当前观测检查，不能凭描述相似就执行。

| 技能档案应记录 | 原因 |
| --- | --- |
| 名称、版本、任务描述、参数单位/范围 | 区分“前进30cm”与“保持前方30cm” |
| API签名、实现哈希、固件构建、校准/底盘配置 | 同一个接口名字不能证明控制行为和物理条件相同 |
| 前置条件、后置条件、停止方式、失败类别 | 对接当前硬件，而非模型猜测 |
| 验证场景、成功与失败样本、误差分布、人工确认 | 一次执行成功不是技能全面可靠 |
| 证据类型：编码器估计 / 独立尺测 / 外部位姿 | 不把流程通过升级为物理任务完成 |

有效性建议：纯界面修复可经判断保留技能；轮径、轮间距、控制方式、校准或固件动作行为改变，应暂停相关条目并重验。不要一律永久失效，也不要仅因API版本没变就默认有效。手动搬动车体使此前方向引用失效；持久技能知识可以保留，但不保存一个虚构的绝对位置。

验收建议：新参数组合先在留出的任务上验证；重复调用仍获得本次反馈；错误技能不因历史成功绕过条件；语义检索误命中只影响候选，不导致误动。该阶段不用开放任意Python循环、动态导入或模型编写电机驱动。

## 7. 开机会话上下文怎样保留而不越来越慢

Thea把稳定身体信息、刷新观测与累计任务上下文区分，并将技能正文按需加载。这比每轮附上所有原始串口日志更适合本车；可借鉴这种生命周期划分，不必整体迁移框架。[Thea](https://github.com/EIT-HAI/Thea)

| 记忆层 | 建议保存 / 更新 | 重启时的处理 |
| --- | --- | --- |
| 完整开机事件账本 | 每个任务、预览/拒绝/完成/失败、实际动作、人工介入与证据 | 保留为历史记录，不能解释新开机“刚才” |
| 模型当前工作上下文 | 稳定能力说明、最新有效状态、近期关键动作、旧任务摘要与可查询引用 | 新boot重新建立，不继承物理状态 |
| 持久技能知识 | 有条件、带版本的验证技能与经验 | 可保留；使用前核对兼容与当前条件 |

这项建议**不是只保留最后几轮、丢掉从开机开始的历史**。完整记录保持不变；模型提示可使用可追溯摘要和按需检索，相关原始任务仍可取回。“转回去”引用明确的已完成动作；“回到刚才位置”目前没有独立定位支持，应继续区分。

最新设备状态优先于过去故障文字；历史失败用于诊断，不直接证明设备现在永久不能运动。用户手动摆放、归零和重启必须成为上下文事件。总结模型不得修改原始动作数值或把失败写成成功。

## 8. 传感器、定位与无线运行的中期选择

### 8.1 先修正观测定义，再追求更多传感器

ToF的−20mm偏移应注明测量基准、校准距离、适用条件与原始值；近场几厘米读数不能用统一偏移承诺贴近精度。姿态3D的排针视角转换是显示变换，车体控制需要独立的安装关系验证；BMI位于左后方本身不要求移到正中心，但“知道安装位置”不等于完成轴向和动态影响校准。[本地校正说明](../docs/POSE_RANGE_CALIBRATION.md)

前向ToF目前可支撑有界接近动作，不足以提供全周障碍物信息。恢复普通前进保护时应先固定朝向、测新鲜度、停车余量、近场和无反射条件，并单独验证；本报告没有打开已按用户要求关闭的保护。

### 8.2 先获得独立验证，再开放位姿接口

近期可用尺测和固定相机做重复轨迹验证；后续可评估AprilTag固定外部相机或车载相机+已知标签。其位姿也需要标定和误差评估，不应直接命名成绝对真值。[AprilTag官方仓库](https://github.com/AprilRobotics/apriltag)

之后才考虑轮式里程计与IMU融合、车体坐标变换、观测不确定性、外部定位修正，以及地图上的任务。里程计可以先作为明确标记的估计量，不能据此自动把实车`task_success`改为true。没有观测和定位前，不开放“去桌边”“绕开障碍”“回到原处”等会暗示空间理解的接口。

### 8.3 消除拖线需要供电与通信两项一起做

无线通信只去掉数据线，独立5V适配器的电源线仍可能拖拽。未来评估车载电源、固定线束与本地网络通信时，应记录续航、供电稳定性、负载和失联行为。当前取消的5V自动检测不在本次重新引入；以后若需要，先明确测量硬件，再谈自动控制限制。

迁移无线后保留单一控制者、序号、短租约、STOP、设备boot身份和认证；不得因“网络偶尔慢”取消停止截止或自动重播指令。先以端到端数据证明瓶颈，再决定传输选择。

## 9. 是否现在全量迁移 ROS 2 / micro-ROS / 大型代理框架

**我的判断：现在先不迁移。** 本车控制链路已经能完成研究所需的有界动作；更大的框架不会补出缺失的地面位置、传感器覆盖和物理验证。当前适合借鉴接口与诊断设计，保留自己的ESP-IDF实时控制。

| 方案 | 适合的触发条件 | 代价与建议 |
| --- | --- | --- |
| 保持当前Python+串口+ESP-IDF | 专注自然语言、复用、底盘验证 | 近期首选；改进契约与记录即可获得清晰实验 |
| 电脑端ROS 2桥接，MCU协议暂保留 | 需要接标准里程计/IMU/测距、ROS工具或相机 | 先做可撤回的适配层；保持独占串口与原停止路径 |
| MCU采用micro-ROS | 需要更完整ROS消息链路并有版本/资源验证 | 与当前IDF5.1.2兼容需验证；agent、构建与通信开销增加 |
| Linorobot2 / Cockpit | 有Linux机器人端、兼容固件配置、定位/建图传感器 | 适合以后导航整合；避免把Windows项目一次性重写 |
| RAI / Thea适配 | 有更多真实能力、可供高层查询的环境与执行后证据 | 先封装现有Backend，比较收益；框架不会代替MCU控制与停止 |

依据：[Linorobot2硬件](https://github.com/linorobot/linorobot2_hardware)、[Cockpit](https://github.com/hippo5329/linorobot2-cockpit)、[micro-ROS组件](https://github.com/micro-ROS/micro_ros_espidf_component)、[RAI](https://github.com/RobotecAI/rai)、[Thea](https://github.com/EIT-HAI/Thea)。这里是选型路径建议，并未保证任何项目直接支持本车现有驱动和全部引脚。

## 10. 可形成有价值结论的实验

CaP-X提示了一个值得注意的方向：API抽象层本身会影响代理表现。这个项目能比较“模型重新生成完整程序”“检索已验证完整Policy”“参数化技能组合”，同时记录物理误差与软件完成，而不仅比较哪个模型写得更快。[CaP-X论文](https://arxiv.org/abs/2603.22435)

| 问题 | 对照设计建议 | 结果必须记录 |
| --- | --- | --- |
| 复用能否降低响应成本而保持行为 | 不复用 / 当前完整复用 / 未来参数化技能；分别留出新参数和新表达 | 请求数、Token、p50/p95、拒绝/误动作、物理误差、命中和失效原因 |
| 上下文是否帮助“转回去” | 无上下文 / 当前开机上下文 / 可追溯分层上下文 | 正确引用率、重启/手动移动后的拒绝、误引用、提示长度与延迟 |
| 抽象层如何影响计划 | 当前字面量原语 / 经批准的技能配方，保持相同动作预算 | 校验错误、计划长度、实际运动数、独立任务结果 |
| 段间审核值得多少耗时 | 本地审核 / 模型审核，使用同一反馈录制片段和允许的实车任务 | 漏报/误报、继续/中止决定、等待和调用成本；不以自动重试换成功率 |
| 参数与地面变化有何影响 | 固定地面/拖线条件的重复动作；用模拟加入噪声、反馈丢失与延迟 | 全部成功与失败、停稳余量、估计与独立测量差异 |

仿真负责便宜的故障与候选筛选；实车负责受控重复验证。开发与测试任务分开，技能不要只在自己见过的任务上获得“验证”。不复制外部论文的任务数、成功率或仿真收益来给本车背书。

建议对“转回去”、半圈拆成两次、后退、目标净距、无效传感器、复位和手动介入单列回归任务。本车提示已经说明两次90°的组合；下一步研究应验证语义与预算是否稳定，而不是把已有提示写成待开发接口。

## 11. 分阶段路线和暂缓事项

以下是建议阶段，不是承诺工期。每阶段完成条件达成后再扩展；本次未实现任何条目。

| 阶段 | 优先事项 | 完成条件建议 |
| --- | --- | --- |
| A：现有实车稳定 | 复核v2高PWM、模式/故障契约、固定传感器、停止与校准记录 | 有明确测试条件和重复结果；误判与物理异常能分开解释 |
| B：延迟与诊断 | 统一时间线、故障回放、串口与控制耗时分析 | 能定位慢在模型、等待、传输还是驱动；回放不驱动车辆 |
| C：技能和记忆 | 版本化参数技能、前后置条件、开机账本与工作上下文 | 在留出任务上验证，过期/不兼容条目不误执行 |
| D：独立观测 | 外部位置验证、里程计/IMU安装关系、通信与供电稳定 | 能报告位置估计误差和观测不确定性，不再仅看编码器成功 |
| E：空间任务与可选ROS | 真实地图/定位后，适配导航和更丰富高层工具 | 感知、规划、控制与任务评估各自有真实接口与证据 |

当前暂缓：任意生成代码直接上车；模型修改运行中控制器/保护阈值；自动尝试清除硬件故障；完整VLA训练；没有定位就自主探索/地图导航；把向量检索相似度当成执行许可；把网页端往返耗时当成轮子总延迟；在没有校准证据时声称高PWM或高精度已经验证。

**最推荐的下一个小里程碑：** 不先增加模型功能，先完成一次有条件记录的短动作/停稳验证，并把它变成可回放的Episode；随后为一类已实现动作定义参数化技能契约。在已知能力上减少等待和重复生成，比现在全量接入大框架更容易形成可测量收益。
