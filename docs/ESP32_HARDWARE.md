# ESP32 实车接口：v1.8 参数控制与环节计时

硬件及接线沿用已经验证的 ESP32-S3、TB6612、双 N20 编码电机及固定的 BMI323。电脑使用 COM5。测距尚未固定，当前固件暂停 VL53L1X 采样与前方障碍物停车保护，READY 必须为 `firmware=1.8 protocol=PARAM1 front_guard=OFF`。从 v1.7 升级需要重新烧录，后续连续任务不需重复烧录。完整源码现位于仓库内 `firmware/esp32s3/`；原开发机旧工程及其备份保留在本地，不依赖它即可构建。

已有底层动作接入 Robot_Cap 的可信运行时和独立策略进程。`--demo` 使用固定策略；`--instruction` 通过 DeepSeek 生成受限实车策略，默认仅预览，加 `--execute` 才执行。两者都使用相同的串口后端，不使用虚拟世界评分。

## 升级固件一次

关闭旧控制终端和串口 monitor，拔掉电机5V，保留USB。在 VS Code 的 ESP-IDF 终端运行：

```powershell
Set-Location 'D:\Robot_Cap'
idf.py -C firmware/esp32s3 build
idf.py -C firmware/esp32s3 -p COM5 flash
```

烧录完成后接回电机5V，保持车体静止校准，然后启动下面的连续控制终端。新电脑程序要求 v1.8/PARAM1，遇到旧版本会拒绝运动，不退回旧指令尝试。完整构建说明见[固件README](../firmware/esp32s3/README.md)，旧已知版本的升级包保留在[legacy目录](../firmware/legacy/v1.8-upgrade/README.md)。

## 自然语言控制

默认使用 `deepseek-flash` 和项目先前使用的 `https://api.deepseek.com` 接口。优先读取终端的 `LLM_API_KEY`（也接受 `DEEPSEEK_API_KEY`）；没有设置时，程序在本机提示隐藏输入 API Key，仅在本次进程中使用，不写入日志或项目文件。无需把密钥发到聊天里。可用 `--model` 和 `--base-url` 覆盖模型及接口地址；接口地址也沿用 `LLM_BASE_URL`。

先预览，**不会打开串口**：

```powershell
& 'D:\Espressif\python_env\idf5.1_py3.11_env\Scripts\python.exe' 'D:\Robot_Cap\physical_control.py' --instruction '前进30厘米，再左转90度，最后停止'
```

要让小车执行，在关闭旧串口程序、静止校准、动作方向留出空间后运行：

```powershell
& 'D:\Espressif\python_env\idf5.1_py3.11_env\Scripts\python.exe' 'D:\Robot_Cap\physical_control.py' --port COM5 --instruction '前进30厘米，再左转90度，最后停止' --execute
```

该命令会重新请求模型，打印本次生成的代码，通过整段校验后连接 ESP32 并执行。预览与执行分别生成，不是复用上一次预览文件。T/Q、Ctrl+C、BOOT 的停止逻辑沿用原来的实车入口。测距和前方停车保护仍然关闭；首次须升级 v1.8 固件。

当前指令示例：“前进20厘米后停止”“右转45度后停止”“前进10厘米，然后左转90度，再左转90度，最后停止”。每次最多三个运动动作，结尾必须 `robot.stop()`。只允许直接调用和数值参数；循环、条件、变量、观测、范围外距离/角度、自定义速度都会在打开串口前被拒绝，即使前面的动作本来有效，也不会先执行前面部分。

模型负责理解自然语言，提示词要求拒绝不支持的任务，不擅自近似或拆分；代码校验核对输出的能力、参数和预算，并不独立证明它理解了原句。日志保存指令、生成策略、校验结果、模型/token/耗时信息及实车反馈。API 失败或输出不合法时没有串口动作；不会重试运动，也不会改用固定演示冒充模型结果。

## 连续输入任务

启动一次，输入一次 API Key，逐条输入任务即可。运行下面的命令后，每次在 `任务 >` 后输入一句话并回车，会生成、校验并执行：

```powershell
& 'D:\Espressif\python_env\idf5.1_py3.11_env\Scripts\python.exe' 'D:\Robot_Cap\physical_control.py' --port COM5 --interactive --execute
```

例如先输入 `前进10厘米，然后左转90度，再左转90度，最后停止`，完成后再输入 `右转90度，最后停止`。动作范围保持不变：每条最多三个运动动作加停止。车完成整段动作、确认健康停稳后才接收下一条；不会在行驶时排队执行任务。终端保持焦点，执行期间输入的普通字符会被丢弃，不要粘贴多条任务。

- 待命输入时：`status` 回车查看反馈；`T` 回车直接停止并确认停稳；`Q` 回车确认停止后退出。这些命令不请求模型。
- 生成或执行时：直接按 `T` 或 `Q`，立即请求停止，取消剩余动作并结束会话。Ctrl+C、BOOT 也可停止；停止后的会话不自动恢复运动。
- 生成失败或代码校验失败：本次不发送运动，若串口仍健康停稳，可以输入一条新任务。
- BOOT 停止、动作失败、超时、复位或断线：结束会话，不自动重连或续跑。断线时仍不能保证停止字节送达。

串口在正常会话中只打开一次。每条生成的策略通过校验后，终端还会发送停止并等待新的停稳 READY，避免使用长时间待命前的旧确认。仅在新的人为任务且连接健康、READY 和停稳均确认时，可信终端才重置本条任务的动作预算；这个操作不开放给生成的代码，也不清除任何故障或停止锁定。模型接收真实连接/停稳状态和本次会话的近期任务摘要，不提供虚拟位姿。取消后的模型请求即使稍后返回，也不会发送动作。

去掉 `--execute` 是连续预览模式，整个会话不打开串口。会话日志仍写入 `runs/physical/`，每条任务保存指令、代码、模型指标、执行反馈及 trace；正常退出也确认停车。密钥只保留在本次进程内。升级 v1.8 后无需每条任务重复烧录，测距保护仍然关闭。

三次运动支持只修改电脑端，现有 v1.8/PARAM1 固件无需重新烧录。退出正在运行的旧控制终端，再执行上述命令。明确要求的有限重复会展开为直接调用，例如：

```python
robot.move(0.10)
robot.turn(90)
robot.turn(90)
robot.stop()
```

每次转弯都以本次开始时的角度为基准，执行并等待停稳，然后开始下一步。单次转弯范围保持15–90°，不允许模型自行把一个超范围动作拆分来绕过限制；可以明确说“左转90度，再左转90度”或“分两次左转半圈”，但单次180°仍不支持。循环和无限重复仍拒绝。三个运动都完成后再发结尾STOP，停稳确认和计时仍保留。

## 统一入口与分段任务（2026-10-12）

已运行的 v1.8/PARAM1 固件可直接使用，**本次不用重新烧录**。默认 `main.py` 仍是模拟模式；加 `--backend esp32` 会转入实车入口，仅注册硬件支持的能力，不读取虚拟地图或使用虚拟任务评分。模拟模式的 `--auto` 不适用于实车，实车须显式使用 `--execute`。

分段任务启动命令：

```powershell
& 'D:\Espressif\python_env\idf5.1_py3.11_env\Scripts\python.exe' 'D:\Robot_Cap\main.py' --backend esp32 --port COM5 --interactive --mission --execute
```

输入 `前进10厘米，左转30度，右转30度，再前进10厘米，最后停止` 可验证两段流程：第一段执行前三个运动并确认停稳，将本段实际反馈交给模型决定继续或中止，继续后第二段执行剩下的前进并停止。运动范围仍为每次前进5–30厘米、左右转15–90度；模型提示词仍要求拒绝范围外参数、后退、未明确要求的拆分及自主导航。

整项计划最多9个运动调用，执行前完整校验，后面存在非法动作也不会先执行前段。每段最多3个运动加STOP，经原有 Validator、独立 Worker、Runtime、串口后端执行。每个运动仍等待有效结果和停稳READY；段间额外等待本段STOP确认。模型决策只接受 `CONTINUE` 或 `ABORT: 原因`，不能生成新动作、改动顺序、重复已执行动作或跳过剩余动作。模型判断只是基于反馈继续执行原计划，不包含定位、路线重规划或误差纠偏。

整项任务从初次模型请求开始，固定限时180秒，包含所有模型请求、Worker和串口等待；PC独立计时线程在超时时请求停止并禁止剩余动作。总运动预算跨段累计，不随每段后端预算更新而增加。动作失败、无效模型回复、模型中止、超时、T/Q/Ctrl+C/BOOT均结束会话，不自动续跑。测距与前方停车保护仍关闭，反馈是编码器/相对陀螺仪估计，不能证明实际地面位置或路径无碰撞。

省略 `--execute` 为分段预览：仅生成并完整校验计划，不打开串口，不编造执行结果，也不请求段间反馈决策。旧连续命令不加 `--mission` 时仍限制每任务3个运动加STOP。

日志沿用 `runs/physical/`，每项任务增加 `mission_limits`、`segment_policies`、`segments`、`reviews`、`completed_motion_calls` 和超时状态；段记录保存实际Worker trace，反馈决策记录保存输入摘要及决策。任务级计时增加所有段间模型反馈决策的累计耗时，动作前停稳与策略执行耗时按段累计；各段保留独立计时。反馈决策等待总耗时包含模型请求与PC等待开销，两者不能相加。整项计划执行完成的 `execution_success=true` 不替代独立地面测量，`task_success` 仍为 `null`。

## 连续任务上下文

连续终端现在向模型提供最近4条任务的摘要，并单独保留最近完整完成的运动任务：用户指令、任务状态、实际完成的动作参数以及编码器/陀螺仪反馈。摘要不包含原始串口日志、代码或密钥，当前任务不会被放进自己的历史。每条日志的 `model_history` 保存本次实际提供的历史，便于核对。

例如在同一次会话中依次输入：

```text
左转45度，最后停止
再转回去
```

第二条应生成 `robot.turn(-45)` 加 `robot.stop()`。若上一条完成的是前进10厘米、左转90°、再左转90°，“再转回去”对应两次右转90°加停止；前进动作不会被倒退撤销。转角依据之前请求的角度，实际测得的偏差作为反馈，不自动改成超范围的转角。它表示反向执行上一条任务的转弯，不承诺恢复准确地面位置或绝对朝向。

历史区分 `completed`（完整执行并确认停止）、`rejected_without_motion`（拒绝且没有动作）、`preview_not_executed`（仅预览）、`failed`、`interrupted` 和 `unconfirmed`。拒绝的任务不会覆盖已完成转弯；存在后续失败/未确认运动时，不提供旧的反向参考，也不自动补跑剩余动作。最近完成任务只有前进、没有转弯时，“转回去”缺少明确参考，会要求用户指定角度方向。

上下文只属于当前终端进程，退出、重连后从空历史开始，不自动加载旧日志。如果手动转动车体，需重新明确角度和方向。更改电脑程序后在旧终端输入Q回车，再启动连续命令，无需重新烧录 v1.8。

模型利用历史解释“再来一次”“转回去”等指代；生成的整段代码仍经过原有校验，普通模式每条最多三个运动加停止，分段模式遵守9运动总预算，距离/转角限制、停止逻辑和测距关闭状态保持不变。模型对语言的理解没有独立地面真值证明，执行前仍打印本次生成的动作。

## 运行一次实车策略

1. 在旧控制终端按 Q 退出，关闭 idf.py monitor 等占用 COM5 的工具。车平放在地面，前方及左侧留出空间，USB 和电源线有足够松量、避开轮子。BMI 上电校准期间保持静止。
2. USB 与电机独立 5V 按原接线连接。在 PowerShell 运行下面的命令；该 `--demo` 命令会在收到停稳 READY 后自动执行一次动作组合。

```powershell
& 'D:\Espressif\python_env\idf5.1_py3.11_env\Scripts\python.exe' 'D:\Robot_Cap\physical_control.py' --port COM5 --demo
```

执行的策略是：

```python
robot.move(0.30)
robot.turn(90)
robot.stop()
```

终端需保持焦点，英文输入；按 T 或 Q 中止，取消剩余动作，按 BOOT 也可停止。不需要长按 BOOT 解锁。Ctrl+C 也请求停止并退出。前方没有测距停车保护，本轮由用户实时监看。

如果只检查连接，去掉 `--demo`。程序默认只发送 STOP，不发送运动指令。

运行完成会打印各动作反馈、状态和日志路径；请发回结果或对应 `runs/physical/日期-时间.json`。测量值是编码器/陀螺仪估计，线材拖拽和打滑影响地面动作，不据此自动重调标定。

## 当前开放的 API

| 调用 | 范围与语义 |
| --- | --- |
| `robot.move(distance)` | 前进0.05–0.30m，参数步长0.001m；底层固定速度，编码器均值达到本次目标关闭驱动；等待有效结果与新的停稳 READY |
| `robot.turn(angle)` | +15–+90°左转，−90–−15°右转，参数步长0.1°；等待有效结果、误差在±5°内及停稳 READY |
| `robot.stop()` | 立即发送T，再等待驱动关闭确认和停稳 READY |
| `robot.get_state()` | 连接、ready、stopped、动作数和故障；stopped可能未知，无虚构坐标或碰撞结果 |

范围外距离、转角、后退和自定义速度会被拒绝，不拆成重复动作冒充任意距离。测距与定位接口不进入本轮能力清单；直接访问同样报不可用。原模拟器和 Benchmark 的 API、默认入口不受影响。

## 执行与停止

主进程独占串口，策略进程仅持有受限 RobotProxy。实车 Registry 明确约束参数和超时：move 9秒、turn 6秒，包含等待反馈及停稳；固件运动本身仍为 F 最长6秒、J/L最长3秒。动作失败会向策略返回异常，使后续调用停止。

开串口前设置 DTR/RTS 为 False；打开后清除已有接收缓冲、发送T，必须收到该次停止确认和随后兼容模式 READY，才允许运动。部分 USB 串口桥仍可能在打开时复位；运行期间发现复位就中止，需要用户重新启动程序，不自动恢复。

一个运动命令必须依次收到匹配的 START、目标 STOP、有效 RESULT、DONE，随后收到新的停稳 READY。缺失、错误、BOOT/T停止、反馈失效、超时或断线都会中止该会话的后续运动。固定演示仍为两个运动加停止；普通模式每条最多三个运动加结尾停止，共4次普通调用；分段模式整项最多9运动，每段仍最多3运动+STOP，超限整段拒绝；安全停止始终可发送。串口停止写入有200ms超时，不等待运动处理器的普通动作锁。

固件没有 command ID，因此要求独占串口、单次执行、无运动重试。Runtime 同一 command ID 的重试返回缓存结果；程序重启后的新命令属于新任务，不跨会话去重。没有触发故障后的自动续跑。

USB断开后停止字节可能无法到达，不能把“发送T”当作停车确认；已开始动作仍受固件目标与时间上限约束。反馈状态的 `stopped=true` 需要 READY 确认，写入T本身只将其变为未知。

日志分开记录 `execution_success` 与 `task_success`。前者表示接口执行完成；后者本轮为null，因为没有独立地面定位、真值评分或碰撞检测，不用虚拟世界坐标替代实测位置。

## 各环节计时

终端自动显示中文环节耗时（秒），JSON 使用 `timings_ms`（毫秒），来自高精度单调计时器。单次入口记录模型请求、整段代码校验、串口连接/握手、策略执行和任务总耗时；连续入口只在启动时记录一次握手，每条任务另外记录动作前停止/停稳确认。总耗时从开始处理指令到清理本次任务，排除用户输入任务、输入密钥的等待。

每个运动动作的结果还包含：

| 字段 | 含义 |
| --- | --- |
| `serial_start_wait` | 发送指令到收到匹配START |
| `host_start_to_cutoff` | 电脑收到START到收到目标STOP |
| `firmware_drive` | 固件测量的驱动启动到关闭时间；沿用结果中的 `elapsed_ms` |
| `cutoff_to_report` | 收到目标STOP到收到停驱动后的测量结果（固件在关闭后300ms采样） |
| `report_to_done` | 收到结果到收到完成确认 |
| `done_to_stopped_ready` | 完成确认到收到新的停稳READY |
| `action_total` | 发指令到停稳READY的总等待时间 |

STOP结果记录 `serial_stop_ack_wait`、`ack_to_stopped_ready` 和 `action_total`。串口阶段是电脑接收时间，包含串口传输、缓冲和调度；不能当成轮子物理停止的精确时间。`firmware_drive` 与电脑测量的驱动阶段重叠，`policy_execution` 也包含动作与子进程开销，不能把这些字段全部相加。

生成被拒绝或API报错时，已完成的请求/校验时间仍写入日志；中止尚未结束的请求只记 `generation_until_cancel`，不等待模型，也不把后台晚到结果写入已结束任务。失败动作不会伪造完成阶段，原始串口日志和任务总耗时仍保留。

## 参数串口协议

`@F200\n` 表示前进200mm，`@J450\n` / `@L450\n` 表示左/右转45.0°。固件允许分段接收，只有完整换行帧通过数值范围检查才启动；帧超时250ms、混合多动作、非法数值会关闭驱动并拒绝，T始终优先。运动期间收到的新动作不会排队。原单字节F/J/L仍是300mm/90°，用于旧键盘程序；当前后端核对START和RESULT中的目标，不能用旧固定目标冒充新参数执行成功。

参数分辨率不等于地面精度。30cm/90°以及部分10cm/30°/45°参数已有用户实车反馈；分段模式于2026-10-12也完成一次两段任务。各参数的统计精度和真实地面位置仍需独立测量。

## 程序接入方式

```python
from robot.backends.esp32_serial import ESP32SerialBackend, build_esp32_registry
from robot.runtime import RobotRuntime

backend = ESP32SerialBackend('COM5', max_actions=4)
try:
    backend.connect()
    runtime = RobotRuntime(backend, registry=build_esp32_registry(backend))
    # 由原有 PolicyExecutor/RobotProxy 调用上述能力。
finally:
    backend.close()
```

实车必须使用 `build_esp32_registry`；默认模拟能力清单允许更多参数、默认动作超时也不同。不要把这个测试后端直接传给默认模拟入口或导航评分器。

普通 Python 环境可用 `python -m pip install -e ".[hardware]"` 安装 pyserial。用户已有 ESP-IDF 环境包含该依赖，上面的直接运行命令即可。
