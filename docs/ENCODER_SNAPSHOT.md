# 编码器采样一致性修正（pwm-stream-v4）

## 故障证据与边界

2026-10-13 用户先后报告 A/B 两轮触发 `QUADRATURE_VS_C1_C2_EDGE_SUM_MISMATCH`。后一例的网页串口记录显示：启动前两轮静止，使用直接手动 PWM 100% 向前，约 294ms 后 B 轮触发保护。前面的有效控制帧中，方向修正后的正交增量和边沿总数一致。被拒绝的那一帧以前不写入 trace，因此现有记录不能证明是信号干扰、回摆或读取时序造成。

代码中每轮使用两个独立 PCNT 单元，一个计带方向的四倍频正交计数，一个计 C1/C2 总边沿。旧实现依次各读一次；任务/中断打断可能把两个读数错开，速度越高，错开的计数越多。ESP-IDF 单个读数的内部锁并不使两次 API 调用成为同时采样。这是代码中可复现的误判来源，但尚不能认定为此次实机故障的唯一原因。

参考：[Espressif PCNT 文档](https://docs.espressif.com/projects/esp-idf/en/v5.1.2/esp32s3/api-reference/peripherals/pcnt.html)。当前 IDF 5.1.2 的本地 `pulse_cnt.c` 同样使用每个单元独立的锁。

## 修改

`encoder_snapshot.h` 依次读取 Q0、E0、Q1、E1；仅在正交计数变化不超过 1、总边沿变化为 0 或 1 时发布 Q1/E0。较宽的窗口最多重新采样三次，不清零计数器，不重新执行运动，也不改变 `8 + edges/100` 的计数一致性阈值。

三次均不能取得窄窗口时，运动中关断两轮并锁定 `ENCODER_SNAPSHOT_UNSTABLE`；启动前拒绝使能；手推标定取消当前样本；遥测跳过该样本。无效或半更新的样本不会进入距离、速度和停稳判断。

计数一致性故障增加 `ENCODER_FAULT_FRAME`，输出动作、PWM 模式、方向符号、采样间隔、前后绝对计数、增量、差值和原阈值。先关断驱动，随后打印诊断。原有有效帧 trace 保留。

## 验证与部署

纯 C 测试覆盖：读取间被打断后的重新采样、正反方向、真实计数不一致仍保留、累加器跨界、三次有界失败不发布样本、驱动 API 错误。

```powershell
.\.tmp\encoder_snapshot_check.exe
```

ESP-IDF 5.1.2 编译通过，应用大小 `0x4ee60`，1MB 分区剩余 69%；上述纯 C 测试和原参数/PWM C 回归通过，95 项串口及 PWM 相关 Python 测试在严格警告模式下通过。文档及固件源文件哈希检查通过。

此版本已在用户确认拔下电机独立 5V 后烧录到 COM5，校验哈希通过；停止握手确认 `pwm-stream-v4`、READY、两轮零转速、无故障。BMI 和 ToF 新鲜有效。旧故障记录和同次开机的 5 条任务已归档，复位后新上下文清空，网页进程内密钥保留。

尚未做实车运动验证。烧录必须在电机独立 5V 断开、USB 保留且车静止的状态进行。不能用重开串口清除旧固件锁定，也不能把静止和离线通过当作编码器和供电在运动中已经正常。

## 后续实车反馈：桌面线材越障

烧录 v4 后，用户在有线材的桌面尝试越障。一次直接 PWM 100% 后退停稳后右转的记录，在启动约 94ms 时触发 B 轮保护。新增故障帧：`dt_us=24999 dq=100 forward_dq=100 edges=124 difference=-24 tolerance=9`。前面的有效帧计数一致。该差值大于新采样窄窗口本身允许的错位。

总边沿与带方向净计数相等的前提是基本单向转动。若电信号正常，这组数值对应 112 个正向、12 个反向边沿；轮子越障短暂回弹也可能触发现有检查，不能仅凭报错认定编码器损坏或丢脉冲。尚不能排除电气干扰。用户尚未完成平整无线材区域的 40% 对照，v4 已消除实车故障的结论不成立。

当前没有经过验证的越障模式。不能为支持越障直接提高计数阈值或移除无反馈保护；闭环距离/航向动作与允许回弹的手动控制需要分别设计和验证。
